# 师说 · 四人团队开发协作规范与交付流程 v1.0

> 适用产品：**师说 · AI 双通道课后答疑**（现有 MVP：http://121.37.30.147/ ）
> 产品定位：AI 原生校园生活服务 —— **AI 先答、老师精答**。核心能力 = ①AI + 教师双通道答疑 ②FAQ 自动应答知识库。
> 适用团队：4 人（学生团队，非全职）
> 制定：交付总监（Qi） · 生效日期：2026-11-18 · 复审周期：每迭代回顾会

---

## 0. 文档信息与使用方式

| 项 | 内容 |
|---|---|
| 文档性质 | 团队内部作业标准（SOP），不是给人检查的文档，是给自己用的 |
| 落地位置 | 仓库 `docs/COLLABORATION.md`（本文档即该文件） |
| 强制程度 | 「红线」章节必须遵守；其余为默认做法，团队可在回顾会上改 |
| 修改方式 | 提 PR 改本文档，标题 `docs: 更新协作规范-<要点>`，1 人 review 通过即生效 |
| 现状基线 | 见 §1.3「MVP 现状体检」，本节决定了首个迭代的 P0 |

**使用原则：流程为交付服务，不为流程服务。** 任何环节如果连续两个迭代都没产生价值，回顾会上直接删掉。

## 1. 一页速览

### 1.1 四句话版本

1. **4 个角色**：产品与体验（PO）、前端（FE）、后端与 AI（BE/AI）、测试与交付（QA/Ops）。
2. **1 周 1 迭代**：周一 20:00 计划（30 min）→ 周五 21:00 评审 + 回顾（40 min）→ 周日发布窗口。
3. **1 块看板**：需求池 / 本迭代 / 进行中 / 待验收 / 已完成，**Issue 是唯一任务真相源**，群聊和口头都不算。
4. **1 条红线**：`main` 永远可发布；未经 review 的代码不许进 `main`；发布前必须有回滚方案。

### 1.2 看板列定义（5 列，不多不少）

| 列 | 含义 | 进入条件 | 离开条件 |
|---|---|---|---|
| 需求池 Backlog | 所有想法与问题 | 有人写清一句话 | 计划会被选中 |
| 本迭代 Sprint | 本期承诺 | 通过 DoR（§3.3） | 有人开工 |
| 进行中 Doing | 正在做（**每人最多 1 个**） | 已认领 + 有分支 | PR 提交 |
| 待验收 Review | 等审查/等验收 | PR 已提、CI 通过 | 合并并验收通过 |
| 已完成 Done | 对用户可用 | 通过 DoD（§3.4） | 上线观察 7 天无问题 → 关闭 |

> 禁止增加「测试中」「待联调」等中间列。状态细节写在 Issue 的 checklist 里，看板保持 5 列。

### 1.3 MVP 现状体检（2026-11-18 实测，作为规范输入）

| 探测项 | 实测结果 | 影响 | 对应动作 |
|---|---|---|---|
| `GET /api/health` | `{"ok":true,"service":"shishuo","aiConfigured":false,"demoAccounts":true,"teacherRegistration":true,"workspaceRevision":5}` | **AI 通道未配置**，产品核心卖点当前不可用 | Sprint 1 · P0-1 |
| `demoAccounts` | `true`，生产环境开着演示账号 | 任意人可用演示身份登录，数据可被污染 | Sprint 1 · P0-2 |
| 数据层 | **SQLite（`node:sqlite`）+ WAL**，`/opt/shishuo/data/shishuo.db`；工作区是 `workspace_entities` 表中的一个 JSON 文档，`revision` 为乐观锁 | 数据层本身可靠；但备份必须含 `.db` + `-wal` + `-shm` 三个文件，只抄 json 会丢数据 | §9.2 备份 + Sprint 1 · P1-4 |
| 版本控制 | **`/opt/shishuo` 尚不是 git 仓库** | 线上代码改动无法回滚，这是当前最大工程风险 | **Sprint 1 · P0-0（新增，最高优先）** |
| 运行形态 | `systemd` 单元 `shishuo.service`，`WorkingDirectory=/opt/shishuo`，Node 直接监听 80；**服务器未装 nginx** | 发布/回滚绕不开 systemd；不存在反代层可利用 | §9.2 |
| 前端 | Vite + React SPA，产物 `assets/index-*.js`（约 1.4 MB 单包） | 首屏体积大、无代码分割 | Backlog（P2） |
| 已有接口 | auth 全套（注册/登录/邮箱验证码/重置密码）、`ai/chat/completions`、`uploads/image`、`admin/users`、`admin/audit`、`admin/ai-usage`、`jw/`（教务）、`state/revision` | 能力已覆盖「提问—回答—管理—审计」主干 | 首个迭代以**打通与加固**为主，不新增大模块 |
| 已有业务动作 | 新建提问、删除提问、新增/编辑/删除 FAQ、反馈、更新课程公告 | FAQ 知识库 CRUD 已有雏形 | 只补「命中率评测」与「引用溯源」 |
| 响应头 | 无 `Server` 头，`X-Frame-Options: DENY` 已设 | 基础安全头已具备 | 保持 |

> **结论：现阶段不缺功能，缺的是「AI 真的能答」+「上线有护栏」。** 首个迭代不做大重构。

## 2. 团队角色与职责（4 人）

| 代号 | 角色 | 姓名 | 主责（Owner） | 兼责（Backup） |
|---|---|---|---|---|
| **PO** | 产品与体验 | 许清楚 | 需求池、优先级、验收标准、UI/文案、用户访谈 | 验收测试用例（业务侧） |
| **FE** | 前端 | 甲 | 学生端/教师端 Web、交互与状态、埋点 | 冒烟用例维护 |
| **BE** | 后端与 AI | 乙 | API、鉴权、数据存储、LLM 接入、FAQ 检索/RAG | 部署脚本 |
| **QA** | 测试与交付 | 严过关 | 测试用例、缺陷跟踪、发布/回滚、监控、文档归档 | 前端次要页面 |

### 2.1 决策权（避免"谁都能定，最后没人定"）

| 决策事项 | 决策人 | 需要谁同意 | 备注 |
|---|---|---|---|
| 需求做不做、优先级 | **PO** | 无人可否决，但 BE/FE 可提"成本异议"，异议 >1 天工作量则计划会当场裁 | 一句话理由记在 Issue |
| 技术选型、接口契约、数据结构 | **BE** | FE 同意（影响前端则必须双方签字） | 契约变更走 §6.5 |
| UI/交互细节 | **FE** | PO 同意 | 争议 15 min 内定，不拖 |
| 是否可发布、是否回滚 | **QA** | PO 确认业务影响 | 发布权在 QA，不在写代码的人 |
| 迭代范围变更（中途加需求） | **PO** | 必须换出等量任务 | 只换不加（§5.4） |

### 2.2 岗位说明书（含"不做什么"）

**PO · 产品与体验**
- 做：把用户吐槽变成带验收标准的需求卡；每周至少 2 次真实用户接触（同学/老师）；维护 FAQ 内容质量。
- 不做：不写代码、不定技术方案、不当"需求传声筒"（只转述不判断）。
- 交付物：`Issue(需求)` + 验收标准 + 原型/文案。

**FE · 前端**
- 做：页面实现、接口对接、状态管理、错误与空态处理、移动端适配（校园场景以手机为主）。
- 不做：不擅自改接口字段（改则走契约变更）、不把业务规则写死在前端。
- 交付物：可运行页面 + PR + 自测截图。

**BE · 后端与 AI**
- 做：接口实现、鉴权与权限、数据持久化与备份、LLM 调用与降级、FAQ 检索、（后续）向量检索。
- 不做：不吞掉异常返回 200、不在生产直接改数据（改数据必须留脚本与记录）。
- 交付物：接口 + 迁移/备份脚本 + 接口文档（`docs/api.md`）。

**QA · 测试与交付**
- 做：用例设计、冒烟执行、缺陷定级与跟踪、发布与回滚、健康巡检、文档归档。
- 不做：不替开发改业务代码（可改测试代码）、不做"点一遍没问题"的验收。
- 交付物：用例集 + 测试报告 + 发布记录 + 回滚预案。

### 2.3 单人失效（Bus Factor）对冲

- 每个模块在 Issue 里标注 `owner` 与 `backup`，backup 必须能跑通该模块的启动命令。
- 所有环境变量、密钥位置、部署命令只写在 `docs/RUNBOOK.md`，**不许只存在某人脑子里**。
- 每迭代至少 1 次「交叉 review」：FE 看 BE 的 PR，BE 看 FE 的 PR。

## 3. 需求从收集到上线（主流程）

### 3.1 状态机（7 态）

```
收集 → 评审 → 就绪 → 开发中 → 待验收 → 已上线 → 观察(7天) → 关闭
         ↑                ↓
         └──── 打回（信息不足/成本过高）
```

### 3.2 每环节的负责人 / 输入 / 输出 / 完成标准

| # | 环节 | 负责人 | 输入 | 输出 | 完成标准（可判定） | 时限 |
|---|---|---|---|---|---|---|
| 1 | **收集** | 全员（PO 归口） | 用户原话、课堂痛点、老师反馈、缺陷 | Backlog 一条 Issue，标签 `type:feature`/`type:bug` | 有「谁在什么场景遇到什么麻烦」的一句话描述，无解法的空话不算 | 随时，24h 内录入 |
| 2 | **评审** | PO 主持 | Backlog 待评条目 | 条目被标记 `P0/P1/P2/P3` + 粗估工作量 | 每条给出去向：本迭代 / 下迭代 / 不做（写明理由） | 周一计划会 30 min 内 |
| 3 | **就绪（DoR）** | PO + 承接人 | 被选中的条目 | 需求卡（含验收标准 ≥3 条、影响面、原型/文案） | 通过 §3.3 DoR 全部 6 项 | 计划会后 24h 内 |
| 4 | **开发中** | FE / BE | 需求卡 | 分支 + 代码 + 自测记录 | 分支名合规、每日有进展或阻塞说明、WIP=1 | 按估时 |
| 5 | **待验收** | 提交人 → 评审人 | PR | 已合并到 `main` 的代码 + 自测截图 | PR 通过 review 且 CI/冒烟通过 | 提交后 12h 内完成 review |
| 6 | **已上线** | QA | 发布检查表 | 上线记录 + 版本号 + 变更清单 | 通过 §9.1 全部 9 项检查 | 发布窗口内 |
| 7 | **观察** | QA + PO | 线上监控与用户反馈 | 观察记录（7 天） | 无 P0/P1 缺陷、错误率 <1%、AI 可用率 ≥99% | 7 天 |
| 8 | **关闭** | PO | 观察记录 | 关闭 Issue，沉淀到 `docs/` | 相关文档已更新（FAQ 兜底文案 / 用户说明 / 决策记录） | 观察期满当天 |

### 3.3 需求就绪标准 DoR（6 项，缺一不进迭代）

- [ ] **价值可陈述**：一句话说清「谁的问题、解决后他省了什么」
- [ ] **验收标准 ≥3 条且可测**：能写成"给定…当…则…"，不出现"体验更好""更快"这类不可判定词
- [ ] **影响面已标注**：前端 / 后端 / 数据 / 内容（FAQ）四类中勾选，未涉及也要写"无"
- [ ] **方案有落点**：原型图、文案或接口草案至少有一个
- [ ] **工作量 ≤ 2 人日**；超出的必须拆成子任务
- [ ] **owner 与 backup 已指定**

> 不满足 DoR 的卡片停在 Backlog，**不允许"边做边想"**——这是 4 人团队最大的时间黑洞。

### 3.4 完成标准 DoD（Definition of Done，全团队统一口径）

一个任务只有同时满足以下 6 条才算 Done：

1. 代码已合并 `main`，分支已删除
2. 自测通过，PR 里贴了关键路径截图/GIF
3. 对应测试用例已执行并记录结果（新增功能则新增用例）
4. 错误与空态处理到位（网络失败、AI 超时、无数据、无权限 四种必须有兜底 UI）
5. 文档更新：接口变更更新 `docs/api.md`，流程变更更新本文档，运维变更更新 `docs/RUNBOOK.md`
6. 无 P0/P1 缺陷遗留；有 P2/P3 则已建 Issue 并在卡片里互相链接

## 4. 任务拆分与优先级

### 4.1 拆分规则（3 条）

1. **按"可独立上线"切，不按"技术分层"切**。❌「做 AI 模块」→ ✅「AI 首答接口接通并返回引用」「教师端看到待接管队列」。
2. **单任务 ≤ 2 人日**，>2 天必须拆；< 2 小时的碎活合并成一个「清理包」任务。
3. **任务卡标题格式**：`[模块] 动词 + 对象 + 结果`，例如 `[答疑] 教师可一键接管 AI 已答问题`。

模块前缀固定 6 个：`[答疑] [FAQ] [账号] [教师端] [数据] [交付]`，方便看板筛选。

### 4.2 优先级定义与响应要求

| 级别 | 定义 | 是否进迭代 | 响应时限 |
|---|---|---|---|
| **P0** | 核心链路不可用 / 数据或隐私风险 / 安全漏洞 | 立即，插队 | 30 min 内响应，当日修复 |
| **P1** | 核心功能主路径受阻，有临时绕行方案 | 必须进 | 24 h 内响应，本迭代修复 |
| **P2** | 体验问题、次要功能缺失 | 排期进 | 本/下迭代 |
| **P3** | 优化建议、锦上添花 | 可长期停放 | 不承诺 |

**判定口诀**：用户会不会因此**不能用**（P0）→ 会不会**用不下去**（P1）→ 会不会**不好用**（P2）→ 会不会**更好用**（P3）。

### 4.3 价值/成本二轴（计划会 30 秒决策法）

|  | 成本低（≤0.5 人日） | 成本高（>1 人日） |
|---|---|---|
| **价值高** | ✅ 立即做（本迭代必选） | ⚠️ 拆分后做，先做最小可用切片 |
| **价值低** | 🟡 顺手做（低于 2h 就做） | ❌ 不做（进 Backlog 冷冻区，季度清理） |

### 4.4 容量管控（4 人学生团队的关键约束）

- 每人每周**有效开发时间按 8 小时**估算（课业为主，不虚报理想值）。
- 迭代容量 = 4 人 × 8h = **32 人时 ≈ 4 人日**，只排 **70%（约 3 人日）**，留 30% 应对课业冲突与线上问题。
- 任何人同时进行中的任务 **= 1 个**（WIP=1）。卡住了就换，不要并着做三个半成品。

## 5. 迭代节奏

### 5.1 固定节奏表（1 周 = 1 迭代）

| 时间 | 事件 | 时长 | 参与 | 产出 |
|---|---|---|---|---|
| 周一 20:00 | **迭代计划会** | 30 min | 全员 | 本迭代任务列表（Issues 已进 Sprint 列）、每人认领 |
| 周二–周四 | 开发 + 异步站会 | 每日 ≤3 行 | 全员 | Issue 评论更新进展/阻塞 |
| 周四 22:00 | **冻结日（Code Freeze 前置）** | — | FE/BE | 停止合入新功能，只修缺陷 |
| 周五 21:00 | **评审 + 回顾** | 40 min | 全员 | 演示可运行版本、迭代回顾 3 条改进 |
| 周日 20:00–22:00 | **发布窗口** | ≤2 h | QA 主导 | 上线记录 + 版本 tag |
| 次周一起 7 天 | **线上观察** | — | QA + PO | 观察记录，异常转缺陷 |

> **启动迭代（Sprint 1）延长为 2 周**，用于补基础设施（AI 接入、备份、冒烟用例）。之后统一 1 周。

### 5.2 计划会 30 分钟标准议程（不许超时）

1. （5 min）回顾上迭代遗留与线上问题
2. （10 min）逐条过 Backlog 顶部 10 条，PO 给去向
3. （10 min）确认本迭代范围（不超过 3 人日）+ 每人认领 1–2 个任务
4. （5 min）确认本周最大风险与依赖（如教师端要老师配合试用）

### 5.3 评审 + 回顾 40 分钟议程

1. （10 min）**演示**：只演示"能跑的东西"，PPT 和截图不算
2. （10 min）逐条对照验收标准打勾，未达标直接移回 Doing
3. （15 min）**回顾三问**：什么有效 / 什么卡住 / 下迭代改一件什么事（只改一件）
4. （5 min）更新本文档与看板

### 5.4 范围变更规则（中途加需求）

- **只换不加**：要加一个新需求，必须换出一个等量任务，由 PO 当场决定换哪个。
- **P0 例外**：线上 P0 可插队，不换出，但要在站会说明并顺延一个 P2。
- 变更记录写在迭代 Issue 的评论区，一句话即可，不写变更申请单。

### 5.5 迭代命名与版本号

- 迭代：`S1`、`S2`…（Sprint 编号，不复用）
- 版本：`v0.<迭代号>.<补丁号>`，例：S1 结束发布 `v0.1.0`，S1 期间热修 `v0.1.1`
- Tag 格式：`v0.1.0`，附 release note（3 行：新功能 / 修复 / 已知问题）

## 6. 仓库 / 分支 / 提交 / 合并审查

### 6.1 仓库结构（Monorepo 轻量版）

```
shishuo/
├── web/                  # 前端（Vite + React）
├── server/               # 后端（API + AI 调用）
├── docs/
│   ├── COLLABORATION.md  # 本文档
│   ├── api.md            # 接口契约（BE 维护）
│   ├── RUNBOOK.md        # 部署/回滚/环境变量（QA 维护）
│   ├── faq-quality.md    # FAQ 内容规范与评测集（PO 维护）
│   └── decisions/        # 决策记录 ADR（一页纸）
├── scripts/              # 备份、部署、冒烟脚本
└── .github/              # PR/Issue 模板
```

### 6.2 分支模型：主干 + 短分支（不用 Git Flow）

| 分支 | 用途 | 生命周期 | 保护 |
|---|---|---|---|
| `main` | 永远可发布 | 永久 | **受保护**：禁止直推、必须 PR + 1 review + CI 通过 |
| `feat/<模块>-<简述>` | 新功能 | ≤ 3 天 | 无 |
| `fix/<简述>` | 缺陷修复 | ≤ 1 天 | 无 |
| `chore/<简述>` | 配置、脚本、依赖 | ≤ 1 天 | 无 |
| `docs/<简述>` | 文档 | ≤ 1 天 | 无 |

**规则**：
- 分支从 `main` 拉，合并回 `main`，**不设 `develop`**（4 人团队多一层分支只会增加合并痛苦）。
- 分支存活超过 3 天必须拆分或当日合入，避免长期分叉。
- 命名全小写、连字符分隔，例：`feat/qa-teacher-takeover`、`fix/ai-timeout-fallback`。

### 6.3 提交信息规范（Conventional Commits 精简版）

```
<type>(<scope>): <一句话说明>
```

| type | 用于 | 示例 |
|---|---|---|
| `feat` | 新功能 | `feat(ai): 接入双通道首答并返回引用` |
| `fix` | 缺陷 | `fix(auth): 修复验证码过期后仍可登录` |
| `docs` | 文档 | `docs: 补充回滚步骤` |
| `refactor` | 重构（不改行为） | `refactor(api): 抽出统一错误响应` |
| `test` | 测试 | `test(faq): 新增 50 条命中评测用例` |
| `chore` | 构建/依赖/配置 | `chore: 升级 vite 到 5.x` |

- scope 取值：`ai` `faq` `auth` `qa`（答疑）`teacher` `admin` `deploy` `db`
- 说明用中文，**不超过 50 字**，动词开头，不写"修改""更新"这种无信息量的词
- 一次提交只做一件事；发现夹带了无关改动就拆开

### 6.4 合并审查（Pull Request）

**PR 必填模板**（放在 `.github/pull_request_template.md`）：

```markdown
## 关联
Closes #<issue>
## 改了什么（≤3 行）
## 怎么验证（命令/步骤/截图）
## 风险与回滚（影响哪些数据/接口，怎么退）
## 自检
- [ ] 本地跑通、无 console 报错
- [ ] 新增/变更接口已写入 docs/api.md
- [ ] 错误与空态已处理
- [ ] 未提交密钥、调试代码、console.log
```

**审查规则（轻量但不可省）**：

| 项 | 约定 |
|---|---|
| 谁审 | 至少 1 人，**不能是作者本人**；跨模块改动需对应 owner 审 |
| 审什么 | 只审 4 件事：①逻辑正确性 ②接口/数据契约 ③安全（越权、注入、密钥）④可维护性 |
| 不审什么 | 格式与风格交给工具（ESLint/Prettier），人不要争空格 |
| 时限 | 提交后 **12 h 内**给出结论（学生团队允许隔夜，但当日提的次日必须审完） |
| 结论 | 只有三种：`Approve` / `Request changes（写明具体行与原因）` / `Comment`（不阻塞） |
| 合并方式 | **Squash and merge**（保持 `main` 线性历史），合并后删除分支 |
| 冲突处理 | 作者自行 rebase 解决，不把冲突丢给 reviewer |
| 小改动快速通道 | 纯文案/样式/单行修复：可 `self-merge`，但必须在群里发一行说明 + 事后补 review |

**红线（违反即回滚）**：
- ❌ 直推 `main`
- ❌ 提交 `.env`、密钥、数据库文件、`node_modules`
- ❌ 一个 PR 改超过 400 行（超过就拆）
- ❌ 未经 review 上线（P0 热修可先上线，24h 内补 review）

### 6.5 接口契约变更（前后端联调的唯一摩擦点）

- 契约以 `docs/api.md` 为准，**先改文档，再改代码**。
- 变更流程：BE 提 PR 改 `api.md` → FE 在 PR 里回复"确认" → 同 PR 或紧随 PR 改实现。
- 破坏性变更（删字段、改类型）必须**新增字段兼容一版**，下迭代再删。
- 未走流程导致的联调返工，记一次「协作债」，回顾会上说一句即可，不追责。

## 7. 测试用例与验收标准

### 7.1 四层测试（按性价比排序，不追求覆盖率数字）

| 层 | 内容 | 负责人 | 频率 | 通过标准 |
|---|---|---|---|---|
| **L1 冒烟** | 10 条关键路径（§7.2） | QA | 每次发布前 + 每日定时 | 10/10 通过 |
| **L2 接口** | 核心 API 正常 + 异常 + 越权 | BE 写、QA 跑 | 每次 PR（CI） | 全部 2xx/4xx 符合预期 |
| **L3 业务用例** | 手工场景表（学生提问→AI 答→教师接管→采纳） | QA | 每迭代 | 主流程 100% 通过 |
| **L4 AI 效果** | 答案质量评测集（§7.3） | PO 出题、BE 跑 | 每迭代 | 达到阈值 |

> 不做：单元测试覆盖率考核、端到端自动化框架搭建。4 人团队现阶段投入产出不划算，L1+L2 已能拦住 80% 的低级问题。

### 7.2 L1 冒烟清单（10 条，钉死在 `scripts/smoke.md`）

1. `GET /api/health` 返回 `ok:true` 且 `aiConfigured:true`
2. 学生注册 → 邮箱验证码 → 登录成功
3. 学生提出一个问题，列表可见
4. AI 首答返回内容，且响应时间 < 8 s
5. AI 答案展示引用来源（课程/文档 + 位置）
6. 教师端能看到该问题并「一键接管」
7. 教师回答后学生端实时/刷新可见
8. FAQ 新增一条 → 相同问法能被自动命中作答
9. 无权限用户访问 `/api/admin/*` 返回 401/403
10. 移动端（375 px 宽）主流程可用，无横向滚动

### 7.3 L4 AI 效果验收指标（本产品特有，必须量化）

| 指标 | 定义 | 首迭代阈值 | 目标（3 迭代内） |
|---|---|---|---|
| **FAQ 命中率** | 评测集 50 条真实提问中，被 FAQ 直接正确回答的比例 | ≥ 60% | ≥ 85% |
| **引用可溯源率** | 答案中给出可点开的来源与原文位置的比例 | **100%** | 100% |
| **拒答正确率** | 超出课程范围的提问，明确说"暂无法回答并转教师"而非编造 | ≥ 80% | ≥ 95% |
| **首答延迟 P95** | 从提交到首个 token/完整答案 | ≤ 8 s | ≤ 4 s |
| **教师接管率** | AI 答后学生点"没解决"的比例（反向指标） | 记录基线即可 | ≤ 25% |
| **AI 可用率** | 调用成功次数 / 总次数 | ≥ 99% | ≥ 99.5% |

**评测集管理**：`docs/faq-quality.md` 维护 50 条「真实提问 + 期望答案要点 + 来源」。每迭代追加 5 条，**同一问题连续两迭代答错即进 P1 缺陷**。

### 7.4 验收标准写法（PO 必须遵守）

只接受 **Given/When/Then** 或 **可勾选的具体条目**：

> ❌ 「AI 回答要准确」
> ✅ 「给定一门已上传讲义《高等数学 A》第 3 章，当学生问"洛必达法则的适用条件"时，答案须包含"0/0 或 ∞/∞ 型"且给出来源为讲义第 3.2 节；若知识库无相关内容，则回复"暂未收录，已转给老师"并生成待接管任务」

### 7.5 缺陷与用例的关系

- 每条 P0/P1 缺陷修复后，**必须补一条对应用例**（防止回归）。
- 用例不追求数量，追求「每条都对应一个真实会发生的场景」。

## 8. 缺陷跟踪

### 8.1 缺陷卡必填字段

| 字段 | 要求 |
|---|---|
| 标题 | `[模块] 现象 + 条件`，例：`[答疑] 教师接管后学生端不刷新` |
| 环境 | 线上 / 本地 / 测试，含浏览器与账号角色 |
| 重现步骤 | 编号步骤，3–6 步，能稳定复现 |
| 期望 vs 实际 | 两句话对照 |
| 严重级别 | P0–P3（§4.2 同口径） |
| 证据 | 截图 / 录屏 / 请求响应 / 日志片段 |
| 归属 | `module:` 标签 + 指定 owner |

### 8.2 缺陷生命周期

```
新建(New) → 确认(Confirmed) → 修复中(Fixing) → 待验证(Verify) → 关闭(Closed)
                  ↓                                  ↓
              不是缺陷(Won't fix / 设计如此)      验证不通过 → 打回 Fixing
```

- **提出人**：任何人，24h 内录入 Issue（群里说了不算）
- **确认人**：QA（判定级别与归属），**1 个工作日内**
- **修复人**：模块 owner
- **验证人**：QA（不能是修复人）
- **关闭条件**：修复已上线 + 验证通过 + 已补用例

### 8.3 时限与升级

| 级别 | 确认时限 | 修复时限 | 升级机制 |
|---|---|---|---|
| P0 | 1 h | 当日（≤8 h） | 立即群内 @全员，PO 决定是否停发版 |
| P1 | 12 h | 本迭代内 | 每日站会必须提 |
| P2 | 1 天 | 下迭代 | 计划会排期 |
| P3 | 3 天 | 不承诺 | 季度清理一次 |

### 8.4 缺陷处理三原则

1. **先止血再治本**：P0 先回滚/降级（关掉 AI 走教师通道），再排查根因。
2. **不追责，追流程**：每次 P0 只问一句"哪个环节本该拦住它"，答案写进回顾会记录。
3. **同一处连错两次 → 加护栏**：补用例、加校验、加告警，任选其一。

## 9. 发布与回滚

### 9.1 发布检查表（9 项，QA 逐项打勾，缺一项不发）

- [ ] 1. `main` 最新提交的 CI 全绿，冒烟 10/10 通过
- [ ] 2. 变更清单已生成（本版新增/修复/已知问题）
- [ ] 3. **数据已备份**（`state` 文件 + 上传的图片目录，含时间戳）
- [ ] 4. 上一版产物已留存（`releases/<上一版本>` 目录可回退）
- [ ] 5. 环境变量与密钥已在服务器确认（不打印明文）
- [ ] 6. 数据库/状态结构变更脚本已准备**且已准备反向脚本**
- [ ] 7. 回滚命令已写在 `docs/RUNBOOK.md`，且有人实际演练过一次
- [ ] 8. AI 通道可用性已确认（`/api/health` 的 `aiConfigured:true`）
- [ ] 9. PO 已确认业务可接受（演示账号关闭、公告文案就位）

### 9.2 发布方式（贴合当前架构）

**实测现状**（2026-11-18）：`systemd` 单元 `shishuo.service` → `WorkingDirectory=/opt/shishuo` → `node server/index.mjs`，Node **直接监听 80**，服务器**未装 nginx**；代码尚未纳入 git。

因此发布采用**「systemd 重启 + 备份数据 + 保留上一版目录」**的最小方案，不引入容器与编排。目标结构（需在 Sprint 1 内落地）：

```
/opt/shishuo/
├── releases/
│   ├── <时间戳-上一版>/    # 上一版代码（含 dist 与 node_modules，便于秒回滚）
│   └── <时间戳-本次>/      # 本次发布
├── current -> releases/<时间戳-本次>/   # 软链，切换即发布
├── data/
│   ├── shishuo.db          # 备份时必须连同 -wal、-shm 一起
│   └── uploads/
└── .env                    # 不随版本切换，权限 600
```

发布 5 步（每步 < 1 min）：
1. 备份：`systemctl stop shishuo` → `cp data/shishuo.db* /var/backups/` → `cp .env /var/backups/`
2. 解包新版到 `releases/<ts>/`，`npm ci --omit=dev`
3. 切换软链：`ln -sfn releases/<ts> current`
4. 启服务：`systemctl start shishuo`
5. 跑冒烟 10 条 + 看 `/api/health`

> ⚠️ 前提：`shishuo.service` 的 `WorkingDirectory` 要改成 `/opt/shishuo/current`，否则切软链不生效。改动前先在测试时段演练一次。

### 9.3 回滚判定（任一触发立即回滚，不讨论）

| 触发条件 | 阈值 |
|---|---|
| 核心接口 5xx 比例 | > 1%（连续 3 分钟） |
| 登录成功率 | < 95% |
| AI 首答全失败（`aiConfigured:false` 或全部超时） | 立即 |
| 数据写入异常 / 状态文件损坏 / revision 倒退 | 立即 |
| 隐私或越权问题（能读到他人提问、admin 接口无鉴权） | 立即，且当日修复后重新发版 |

### 9.4 回滚操作与事后

- 回滚命令（软链切回上一版）：`ln -sfn releases/<上一版本> current && systemctl reload shishuo`
- **目标：5 分钟内完成回滚**，超过 10 分钟视为回滚预案失败，记 P0 缺陷并复盘。
- 回滚后动作：恢复数据备份（若涉及数据变更）→ 群内通报（现象/影响范围/回滚版本/预计修复时间）→ 建 P0 缺陷 → 次日复盘 15 min。
- **回滚不是失败**，带病上线才是。

### 9.5 线上观察（发布后 7 天）

- 每日 5 分钟巡检：`/api/health`、错误日志前 20 行、AI 调用失败次数、新增缺陷数。
- 巡检记录一句话写在迭代 Issue 下，不建日报。
- 观察期内出现 P0 → 立即修复并重新发版，观察期重置。

## 10. 沟通同步机制

### 10.1 渠道分工（一件事只在一个地方说）

| 渠道 | 用途 | 不要用来说 |
|---|---|---|
| **Issue / 看板** | **任务与缺陷的唯一真相源** | 闲聊、讨论中的想法 |
| **群聊（微信/QQ 群）** | 快问快答、通知、贴截图 | 需求变更（必须回 Issue）、决策（必须落文档） |
| **PR 评论** | 代码层面的讨论 | 需求范围争论 |
| **docs/decisions/** | 一次性决策记录（一页纸 ADR） | 长文方案（那是 PRD） |
| **周会** | 计划、评审、回顾 | 技术细节争论（会下 2 人对齐） |

### 10.2 响应时限（学生团队务实版）

| 类型 | 时限 |
|---|---|
| P0 线上问题 | 30 min 内响应（群里 @ 到人） |
| 白天工作消息 | 4 h 内（上课期间不算） |
| 非紧急消息 | 当日 24:00 前 |
| PR review | 12 h 内 |
| 被 @ 却逾时未回 | 视为弃权，PO 可代为决定 |

### 10.3 异步站会（每日 3 行，20:00 前发群里）

```
昨天：<完成了什么，带 Issue 号>
今天：<要做什么，带 Issue 号>
阻塞：<需要谁配合 / 无>
```
> 超过 3 行就是写日报了，不许。

### 10.4 会议纪律

- 会有议程、有主持人、有结论、有记录（记录就写在对应 Issue 下，不另建文档）。
- **会议不超过 3 个/周**（计划、评审回顾、必要的临时对齐）。临时会 ≤ 15 min，结束必须产出一条 Issue 或一条 ADR。
- 任何"我们回头再定"的事项，当场指定**负责人 + 期限**，否则等于没定。

### 10.5 决策记录 ADR（一页纸，1 分钟内写完）

`docs/decisions/ADR-00X-<标题>.md`：
```markdown
# ADR-001 首迭代不引入向量数据库
日期：2026-11-20  决策人：BE
背景：FAQ 仅 80 条，先验证需求
决定：首迭代用关键词 + 语义关键词匹配，S2 评估 embedding
影响：命中率上限受限，评测集需观察
何时复审：S2 计划会
```

## 11. 文档沉淀

### 11.1 文档清单与归属（每份文档只有一个 owner）

| 文档 | 路径 | Owner | 更新时机 | 完成标准 |
|---|---|---|---|---|
| 协作规范 | `docs/COLLABORATION.md` | QA | 每次回顾会 | 改动已合并 |
| 接口契约 | `docs/api.md` | BE | 接口变更同 PR | 与实现一致，可被 FE 直接对接 |

| FAQ 质量与评测集 | `docs/faq-quality.md` | PO | 每迭代 +5 条 | 评测可复现，阈值有记录 |
| 决策记录 | `docs/decisions/ADR-*.md` | 发起人 | 每次重大决策 | 一页内写完，有复审时点 |
| 发布记录 | `docs/releases/vX.Y.Z.md` | QA | 每次发布 | 含变更清单与已知问题 |
| 用户帮助 | `web/public/help.md` | PO | 功能变化 | 学生/教师各一段，不写技术词 |

### 11.2 文档三条铁律

1. **代码即文档的边界**：接口看 `api.md`，不靠读源码猜。
2. **过期文档比没文档更糟**：功能改了文档没改，视同 P2 缺陷。
3. **写在仓库里，不写在聊天记录里**：群里讨论出的结论，15 分钟内落成 Issue 或 ADR。

### 11.3 迭代结束的沉淀动作（10 分钟）

- 回顾会结论 → 本文档或 ADR
- 新增 FAQ 错误模式 → `faq-quality.md`
- 踩过的坑 → `RUNBOOK.md` 的「常见故障」小节
- 用户原话 → 迭代 Issue 评论（作为下迭代需求素材）

## 14. 避免过度管理：三条红线与三条禁令

### 14.1 我们**不做**的事（写下来防止自我膨胀）

| 不做 | 原因 |
|---|---|
| 不写超过 1 页的 PRD | 4 人团队，需求卡 + 验收标准足够 |
| 不开超过 3 个会/周 | 学生课业为主，会议成本最高 |
| 不做多级审批 | 1 人 review + PO 一次验收，够用 |
| 不做覆盖率考核、不做工时填报 | 无管理收益，只增加摩擦 |
| 不搞 Git Flow、不设 develop 分支 | 分支越多合并越痛 |
| 不建测试环境集群 | 一台服务器 + 目录版本化已足够 |

### 14.2 唯一不能省的 3 件事

1. **`main` 受保护 + 1 人 review**（质量底线）
2. **发布前备份 + 回滚演练**（数据底线）
3. **冒烟 10 条**（可用性底线）

### 14.3 已知风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 4 人 bus factor = 1 | 一人缺席即停摆 | 每模块设 backup；RUNBOOK 可照做部署 |
| AI 调用成本不可控 | 账单失控 | 用 `/api/admin/ai-usage` 每迭代看一次；设单人日调用上限 + 超限降级到 FAQ |
| AI 生成内容不当 | 校园舆情风险 | AI 答案固定标注「AI 生成，仅供参考」；一键举报入口；教师可下架答案 |
| 学生数据（学号/手机号）泄露 | 合规风险 | 最小化采集；管理端接口强制鉴权 + 审计日志；不把真实数据放到演示/测试 |
| 单文件状态存储并发写 | 数据错乱 | 写操作加锁；每日备份；S2 评估迁移到 SQLite/Postgres |
| 课程/教务数据接口依赖校方 | 阻塞开发 | `jw/` 接口做降级：拿不到就用课程公告兜底；不阻塞主流程 |

### 15.3 Git 常用命令（照抄即可）

```bash
# 拉分支

git checkout main && git pull && git branch -d feat/qa-teacher-takeover
```
